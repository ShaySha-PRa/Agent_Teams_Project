## 一、概述

### 1.1 文档定位

本文档定义 Agent 智能文档审核系统中，所有 9 个 HITL（Human-in-the-Loop）操作在 P5 审阅工作台页面上的完整前端 UI 行为规范。每个操作覆盖从用户触发到最终状态落定的全链路：**触发UI** → **API调用** → **乐观更新** → **成功状态** → **失败状态** → **下一状态**。

### 1.2 操作与上游映射总览

| # | 操作 | 所属中断点 | 风险等级 | API 端点 (§五) | 是否可跳过 |
|:--:|------|:--:|:--:|------|:--:|
| 1 | **Approve** | IP-1 | 高 | `POST /risk-flags/{id}/approve` | 不可跳过 |
| 2 | **Edit** | IP-1 | 高 | `POST /risk-flags/{id}/edit` | 不可跳过 |
| 3 | **Reject** | IP-1 | 高 | `POST /risk-flags/{id}/reject` | 不可跳过 |
| 4 | **Batch Approve** | IP-2 | 中 | `POST /risk-flags/batch-approve` | 可批量跳过 |
| 5 | **Spot Check** | IP-2 | 低 | `POST /risk-flags/sample` | 可选 |
| 6 | **Escalate** | IP-1/IP-2 | 低/中 | `POST /risk-flags/{id}/escalate` | 可选 |
| 7 | **Manual Add** | -- | 任意 | `POST /risk-flags/manual` | -- |
| 8 | **Submit** | IP-3 | 全部 | `POST /documents/{id}/submit` | 不可跳过 |
| 9 | **Save Draft** | -- | 全部 | `POST /documents/{id}/save-draft` | 任意时刻 |

### 1.3 适用页面与路由

| 页面 | 路由 | 涉及操作 |
|------|------|---------|
| **P5 审阅工作台** | `/review/{id}/workspace` | 全部 9 操作 |
| P6 报告预览 | `/review/{id}/report` | 仅查看，无操作 |

### 1.4 通用约定

| 项 | 约定 |
|------|------|
| Base URL | `/api/v1` |
| 认证头 | `Authorization: Bearer <JWT>` |
| Content-Type | `application/json` |
| Toast 持续时间 | 成功 3s / 错误 5s / 可撤销 5s |
| 动画时长 | 卡片滑出 300ms / 模式切换 200ms / 乐观更新 0ms（即时） |
| 字符计数下限 | reject_reason / edit_comment / description >= 10 字符 |
| 防抖间隔 | 按钮点击 500ms（防止重复提交） |
| ⚠️ 标记 | 该接口/功能尚未开发，前端需 mock 或使用条件渲染占位 |

## 二、P5 审阅工作台全局状态机

### 2.1 顶层工作台状态

```
                    ┌──────────────┐
                    │  LOADING     │  页面初始化，fetch 数据中
                    └──────┬───────┘
                           │ 数据加载完成
                           ▼
                    ┌──────────────┐
         ┌─────────│    IDLE      │  正常审阅状态，等待用户操作
         │         └──────┬───────┘
         │                │ 用户发起任意操作
         │                ▼
         │         ┌──────────────┐
         │         │  OPERATING   │  任一操作 API 请求进行中
         │         └──┬───┬───┬──┘
         │            │   │   │
         │    ┌───────┘   │   └───────┐
         │    ▼           ▼           ▼
         │ ┌──────┐ ┌──────────┐ ┌───────┐
         │ │SUCCESS│ │OPTIMISTIC│ │ ERROR │
         │ └──┬───┘ └────┬─────┘ └───┬───┘
         │    │          │           │
         │    │    ┌─────┘           │
         │    │    ▼                 │
         │    │ ┌────────────────┐   │
         │    │ │ RECONCILING    │   │ 乐观更新与 API 响应对比
         │    │ └───────┬────────┘   │
         │    │         │            │
         │    │    ┌────┴────┐       │
         │    │    ▼         ▼       │
         │    │ ┌──────┐ ┌──────┐    │
         │    │ │MATCH │ │ROLL  │    │ 回滚 → 恢复原状态
         │    │ │      │ │BACK  │────┤
         │    │ └──┬───┘ └──────┘    │
         │    │    │                 │
         │    └────┼─────────────────┘
         │         │
         │         ▼
         │    ┌──────────────────┐
         │    │ IDLE (next item) │  自动进入下一审批项 / Tab
         │    └──────────────────┘
         │
         └──── 或直接返回 IDLE（操作失败后停留当前项）
```

### 2.2 工作台子状态机（审批卡片层级）

单个审批卡片内部的状态流转：

```
PENDING_REVIEW ──approve──▶ CONFIRMED       (绿色确认勾 + 卡片滑出)
       │
       ├──edit──────────▶ AMENDED          (黄色编辑标记 + 保存修改字段)
       │                        │
       │                        └── 降级后若变 LOW → 卡片从高风险 Tab 移除
       │
       ├──reject─────────▶ REJECTED        (红色驳回标记 + 卡片滑出)
       │
       ├──escalate───────▶ ESCALATED_TO_HIGH (橙色升级标记 + 卡片移入高风险 Tab)
       │
       ├──manual_add─────▶ PENDING_REVIEW   (人工来源标记，加入高风险队列)
       │
       └──batch_approve──▶ UNREVIEWED_AUTO_PASSED (中风险批量标记)
```

### 2.3 全局 UI 元素状态映射

| 元素 | 依赖状态字段 | 可见性/状态逻辑 |
|------|------------|--------------|
| 提交审阅按钮 | `all_high_risk_resolved` | `true` → 启用(蓝色Primary) / `false` → 置灰(disabled) |
| 审批进度条 | `approved_high_risk / total_high_risk` | 百分比 + "已完成 N/M 项高风险审批" |
| 高风险 Tab 徽标 | `total_high_risk - approved_high_risk` | 剩余待审批数 |
| 中风险 Tab 徽标 | `total_medium_risk - reviewed_medium_risk` | 剩余待处理数 |
| 暂存草稿按钮 | 始终启用 | 任意时刻可点击 |
| 键盘快捷键提示条 | 始终显示 | 底部固定浮层 |

## 三、操作 1: Approve — 同意 AI 标记

### 3.1 角色与约束

| 维度 | 说明 |
|------|------|
| 所属中断点 | **IP-1**（高风险强制审批） |
| 前置条件 | RiskFlag.status = `PENDING_REVIEW`，risk_level = `HIGH` |
| 强制性质 | **不可跳过** — 高风险项必须逐条 approve/edit/reject |
| 是否可撤销 | MVP 不可撤销（v2 可考虑 5s 撤销窗口） |

### 3.2 可视化组件

**触发前**（审批卡片底栏）:
```
┌─────────────────────────────────────────────────┐
│ ... (条款定位 / AI 判定 / Playbook 对比区域) ...  │
├─────────────────────────────────────────────────┤
│  [✅ 同意]    [✏️ 编辑]    [❌ 驳回]              │
└─────────────────────────────────────────────────┘
```

**触发后 → 乐观更新 → 成功**:
```
┌─────────────────────────────────────────────────┐
│ ... (卡片内容保持) ...                            │
├─────────────────────────────────────────────────┤
│  ✅ 已确认 — 审阅人: user_001  10:35:22          │
│  [撤销] (v2)                                    │
└─────────────────────────────────────────────────┘
   ↓ 300ms slideOutRight 动画
   → 下一张审批卡片自动展开 (或 "全部高风险已审批完成" 空状态)
```

```

│                                                              │
```

### 3.4 乐观更新与回滚策略细节

```
乐观更新流程
═══════════
Store (内存)                     API (网络)                    UI (DOM)
─────────                       ─────────                    ────────
│                                │                           │
├─ status→"CONFIRMED" ───────────│─────────────────────► 卡片绿色边框
├─ approved_high_risk++ ────────│─────────────────────► Tab徽标-1
├─ all_high_risk_resolved ──────│─────────────────────► 提交按钮启用
├─ push pendingOp ──────────────│                           │
│                                │                           │
│                                ├─ POST /approve ──────►   │
│                                │                           │
│◄── 200 {decision_id,status} ──│                           │
│                                │                           │
├─ reconcil: decision_id匹配 ◄───│─────────────────────► Toast + 滑出
├─ pop pendingOp ───────────────│                           │
│                                │                           │
│                        或:     │                           │
│◄── 409 CONFLICT ──────────────│                           │
│                                │                           │
├─ ROLLBACK: status恢复 ◄───────│─────────────────────► 卡片恢复原状
├─ ROLLBACK: approved-- ◄───────│─────────────────────► Tab徽标+1
├─ pop pendingOp ───────────────│                           │
└─ show error Toast ────────────│─────────────────────► 错误提示

断网恢复策略:
- 页面 visible 时检测 pendingOperations[] 中 "failed" 项
- 自动弹窗: "检测到 N 项未同步的操作，是否重试?"
- 用户确认 → 批量重试 / 用户取消 → 清空 pendingOperations[] + 重新 fetch
```

|------|------|

| 前置条件 | RiskFlag.status = `PENDING_REVIEW` |

### 4.4 乐观更新回滚策略

Edit 的回滚比 Approve 更复杂，因为涉及多字段修改。采取**快照式回滚**：

```
编辑前快照 = {
  status: "PENDING_REVIEW",
  risk_level: "HIGH",
  risk_category: "合规风险",
  suggestion: "...",
  reviewSummary: { ...深拷贝... }
}

乐观更新执行 → 全部应用到 Store → 渲染

若 API 失败:
  1. Store 恢复编辑前快照 (riskFlag.* + reviewSummary.*)
  2. UI 恢复到编辑前完整状态
  3. 表单保留用户输入 (不清空, 方便重试)
  4. 显示错误 Toast + "重试"按钮

若 API 409 (冲突):
  1. 强制 fetch 该 risk_flag 最新状态
  2. 用最新数据覆盖 Store
  3. 显示 Toast: "该标记已被处理，数据已刷新"
  4. 若最新状态 ≠ PENDING_REVIEW → 移出当前审批队列
```

### 6.4 批量操作的回滚策略

Batch Approve 的回滚需要**逐项恢复**：

```
回滚步骤:
1. 遍历 pendingOperation 中的 risk_flag_ids
2. 逐项恢复 riskFlag.status → "PENDING_REVIEW"
3. 摘要恢复: reviewed_medium_risk -= N
4. UI 逐项取消 ✅ (反向动画，每项 50ms)
5. Toast: "批量确认失败 — [错误原因]"
6. 恢复确认对话框，允许用户重试
```

### 7.4 Spot Check 的特殊性

Spot Check 与其他操作不同：它**先读后写**——先获取抽样结果，再对每个抽样项做出判断。

```
Spot Check 关联的后续操作:
1. [确认无风险] → 直接标记该项为 APPROVED_LOW，无额外 API
2. [标记为中风险] → 调用 Edit 接口 (modified_risk_level = MEDIUM)
3. [升级为高风险] → 调用 Escalate 接口 (new_level = HIGH)

→ Spot Check 本身不改变任何 RiskFlag 状态
→ 状态变化由后续的 approve/edit/escalate 操作触发
→ 因此 Spot Check 无乐观更新
```

### 10.5 409 拦截详细前端实现

```typescript
// 伪代码：submit 操作中的 409 拦截
async function handleSubmit(documentId: string) {
  setGlobalState("submitting");  // 全屏 loading

  try {
    const res = await api.post(`/documents/${documentId}/submit`, { comment });

    if (res.code === 0) {
      // 成功 → 跳转 P6
      documentStore.setStatus(documentId, "COMPLETED");
      router.push(`/review/${documentId}/report`);
    }
  } catch (err) {
    if (err.response?.status === 409) {
      // ★ 409 核心处理路径
      const { pending_count, pending_risk_flag_ids } = err.response.data;

      // 1. 恢复 UI
      setGlobalState("idle");
      closeSubmitDialog();

      // 2. 提示用户
      toast.warning(
        `仍有 ${pending_count} 项高风险条款待审批，请完成后重试`,
        { duration: 5000 }
      );

      // 3. 切换到高风险 Tab
      switchToTab("high-risk");

      // 4. 闪烁未审批的卡片
      pending_risk_flag_ids.forEach((id, index) => {
        const cardEl = document.querySelector(`[data-risk-flag-id="${id}"]`);
        if (cardEl) {
          // 延迟闪烁以产生序列效果
          setTimeout(() => {
            cardEl.classList.add("pulse-alert");
            setTimeout(() => cardEl.classList.remove("pulse-alert"), 3000);
          }, index * 200);
        }
      });

      // 5. 刷新摘要数据确保一致性
      await refreshReviewSummary(documentId);

      // 6. 重新评估提交按钮状态
      submitButton.setDisabled(true);

    } else if (err.response?.status === 422) {
      // 校验失败
      setGlobalState("idle");
      toast.error(err.response.data.message);
    } else {
      // 其他错误
      setGlobalState("idle");
      toast.error("提交失败，请重试");
    }
  }
}
```

## 十二、4 层不可跳过约束的前端实现

### 12.1 约束层级总览

| 层级 | 约束位置 | 机制 | 前端实现 |
|:--:|---------|------|---------|
| **L1** | 后端 LangGraph | `interrupt()` 节点永久等待人类响应 | 前端监听 SSE `interrupt.ready` → 渲染审批卡片 |
| **L2** | 后端 API 层 | `POST /submit` 返回 409 若高风险未完 | 前端 catch 409 → Toast + 跳转未审批卡片 |
| **L3** | 前端 UI 层 | 提交按钮 disabled | `all_high_risk_resolved === false` 时按钮置灰 |
| **L4** | 后端并发控制 | 同一审批项不允许并发修改 | 前端收到 409/423 → 提示 "已被其他会话处理" |

### 12.2 L1: interrupt() 前端监听实现

```
SSE 事件: interrupt.ready
─────────────────────────

前端处理:
1. 解析 event.data:
   {
     interrupt_id: "ip_001",
     interrupt_type: "IP-1",
     payload: { clause_id, risk_level, risk_category, ... }
   }

2. 根据 interrupt_type 分发:
   - IP-1 (高风险): 高风险 Tab 新增审批卡片，Tab 徽标 +1
   - IP-2 (中风险): 中风险 Tab 新增审批项 (或批量更新)
   - IP-3 (确认): 不直接渲染 UI，由前端 submit 流程处理

3. Store 更新:
   riskFlags.push(newFlag)
   interrupt_state = "waiting"
   pending_interrupts.push(interrupt_id)

4. UI 渲染:
   - 对应的 Tab 徽标更新
   - 新卡片插入队列
   - 工作台顶栏进度条更新
```

### 12.4 L3: UI 置灰实现

```
提交按钮的状态计算逻辑:

const canSubmit = useMemo(() => {
  // 1. 所有高风险已完成
  if (!reviewSummary.all_high_risk_resolved) return false;

  // 2. 没有进行中的操作
  if (globalState !== "IDLE") return false;

  // 3. 没有待同步的操作
  if (pendingOperations.some(op => op.status === "failed")) return false;

  // 4. 文档状态正确
  if (document.status !== "HUMAN_REVIEW") return false;

  return true;
}, [reviewSummary, globalState, pendingOperations, document.status]);

// 按钮渲染:
<Button
  variant="primary"
  disabled={!canSubmit}
  tooltip={
    !reviewSummary.all_high_risk_resolved
      ? `请先完成所有高风险审批 (还剩 ${
          reviewSummary.total_high_risk - reviewSummary.approved_high_risk
        } 项)`
      : undefined
  }
  onClick={handleSubmit}
>
  提交审阅
</Button>
```

### 12.5 L4: 并发锁前端提示

```
场景: 用户 A 和用户 B 同时审核同一文档的同一风险项

用户 A 先提交 approve → 成功
用户 B 稍后提交 approve 同一 rf_id → 后端返回 409

前端处理 (用户 B):
1. catch 409
2. Toast: "⚠️ 该标记已被其他会话处理，数据已刷新"
3. 强制 fetch GET /risk-flags/{id} 最新状态
4. 若 status ≠ PENDING_REVIEW → 卡片自动移除/更新
5. pendingOperations[] 清理
```

### 13.1 键盘快捷键

| 快捷键 | 作用域 | 操作 | 说明 |
|--------|:--:|------|------|
| **J** | 全局 (P5) | 下一风险项 | 焦点移到下一个审批卡片，自动滚动到视口中央，左面板同步高亮 |
| **K** | 全局 (P5) | 上一风险项 | 焦点移到上一个审批卡片 |
| **Enter** | 审批卡片聚焦时 | 确认当前操作 | 当前聚焦 approve → 点击 approve; 编辑模式 → 保存; reject 模态 → 确认驳回 |
| **Esc** | 全局 (P5) | 取消/返回 | 关闭模态对话框 / 退出编辑模式 / 取消焦点 / 清除划选 |
| **Ctrl+S** | 全局 (P5) | 暂存草稿 | 触发 save-draft |
| **1/2/3** | 审批卡片聚焦时 | 快速操作 | `1`→approve, `2`→edit, `3`→reject |
| **Ctrl+Enter** | 编辑模式 | 保存编辑 | 等价于点击 "💾 保存修改" |
| **Tab** | 全局 (P5) | Tab 切换 | 在 高风险/中风险/低风险 Tab 之间切换 |
| **/ (Slash)** | 全局 (P5) | 搜索 | 聚焦左面板文档搜索框 |

**J/K 导航详细行为**:

```
按下 J:
  1. 找到当前聚焦卡片的下一个 PENDING_REVIEW 卡片 (跨 Tab)
  2. 若下一个在当前 Tab 之外 → 自动切换 Tab
  3. 卡片滚动到视口中央: cardEl.scrollIntoView({ behavior: "smooth", block: "center" })
  4. 左面板: 读取 card.clause_location → documentPanel.scrollTo(page, offset) → 高亮对应条款区域
  5. 卡片添加 focus-ring 样式 (蓝色边框 2px + box-shadow)
  6. 更新焦点索引 store.focusedCardIndex

按下 K:
  同上，方向相反

到达边界 (第一项 ↑ / 最后一项 ↓):
  - 保持在当前项
  - Toast (仅首次): "已是第一项" / "已是最后一项"
  - 之后不再 Toast (避免干扰)
```

### 13.2 乐观更新全局策略

```
乐观更新适用条件:
✅ approve      → 适用 (即时卡状态变更 + 自动推进)
✅ edit         → 适用 (即时卡状态变更，采用快照式回滚)
✅ reject       → 适用 (即时卡移除，回滚时重新插入)
✅ batch_approve→ 适用 (即时批量状态变更，逐项动画)
✅ escalate     → 适用 (即时卡跨 Tab 移动)
✅ manual_add   → 适用 (临时 ID，API 成功后替换)
✅ save_draft   → 适用 (Toast 乐观显示，API 静默失败不影响)
❌ spot_check   → 不适用 (需等 API 返回抽样结果)
❌ submit       → 不适用 (关键操作，必须等 API 确认)

通用回滚策略:
1. 操作前保存快照 (deep clone 受影响的数据)
2. 操作时 push 到 pendingOperations[] 
3. API 成功 → pop + reconcil
4. API 失败 → 快照恢复 + Toast + 重试入口
5. 断网恢复 → 检测 failed 项 → 批量重试
```

### 13.3 pendingOperations 队列管理

```typescript
interface PendingOperation {
  id: string;                    // uuid
  type: OperationType;           // APPROVE | EDIT | REJECT | ...
  riskFlagId: string;            // 目标 RiskFlag (batch 时为首个)
  riskFlagIds?: string[];        // batch 操作的所有 ID
  snapshot: any;                 // 操作前数据快照 (用于回滚)
  optimisticData: any;           // 乐观更新的数据
  status: "pending" | "failed";  // 当前状态
  createdAt: number;             // Date.now()
  retryCount: number;            // 重试次数
}
```

## 十四、中断恢复与异常处理

### 14.1 SSE 连接中断恢复

```
场景: P5 审阅中，SSE 连接断开

┌──────────────────────────────────────────────────────────────┐
│ DETECTION                                                    │
│                                                              │
│ EventSource 触发 onerror 事件                                 │
│ → 前端检测到断连                                              │
│ → 全局状态变为 "RECONNECTING"                                 │
│ → 顶部警告条: "⚠️ 实时连接已断开，正在重连..." + 重连计数       │
│ → 审批操作照常可用 (不阻塞用户审批，只是收不到推送)              │
└─────────────────────────────┬────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│ RECONNECT STRATEGY                                           │
│                                                              │
│ 1. 指数退避重连:                                              │
│    第 1 次: 1s 后重连                                         │
│    第 2 次: 2s 后重连                                         │
│    第 3 次: 4s 后重连                                         │
│    第 4 次: 8s 后重连                                         │
│    第 5 次及以后: 15s 间隔 (最大)                              │
│                                                              │
│ 2. 重连成功:                                                  │
│    → 检查 document.status 是否变化                            │
│    → 若仍为 HUMAN_REVIEW → 恢复正常状态                        │
│    → 若已变为 COMPLETED → 提示用户并跳转 P6                    │
│    → 重新订阅 SSE 事件流                                      │
│                                                              │
│ 3. 重连失败 (超过最大重试):                                    │
│    → 警告条变为: "⚠️ 无法连接服务器，请刷新页面"               │
│    → 不丢失用户数据 (Store 在内存中)                           │
│    → 自动触发 save-draft (beacon)                            │
└─────────────────────────────┬────────────────────────────────┘
```

### 14.2 页面刷新/重新打开恢复

```
场景: 用户在 HUMAN_REVIEW 状态下刷新页面或重新打开

恢复流程:
1. 页面加载 → fetch GET /documents/{id}
2. 检测 document.status === "HUMAN_REVIEW"
3. → 自动进入 P5 审阅工作台
4. → fetch GET /documents/{id}/risk-flags (获取所有风险标记当前状态)
5. → fetch GET /documents/{id}/review-summary (获取审批进度)
6. → connect SSE (GET /documents/{id}/events)
7. → 渲染已审批项 (灰色/已确认) + 未审批项 (待操作)
8. → 恢复键盘焦点到第一个未审批项

特殊: 检测 pendingOperations[] 中 failed 项:
  → 提示: "检测到 2 项未同步的操作，是否重试?"
  → [重试全部] [忽略]
  → 若重试: 批量调用对应 API
  → 若忽略: 清空 pendingOperations[] + 重新 fetch 最新数据
```

### 14.3 网络断开 (操作进行中)

```
场景: 用户点击 approve → API 请求进行中 → 网络断开

处理:
1. API 请求超时 (10s) 或 fetch 抛出 NetworkError
2. 回滚乐观更新 (恢复原状态)
3. pendingOperations[id].status = "failed"
4. Toast: "⚠️ 网络连接异常，操作已暂存"
5. 断网指示器: 底部浮层 "📡 网络已断开"
6. 网络恢复时 (window online event):
   → 自动重试 failed 操作
   → 或提示用户手动重试
```

### 14.4 浏览器性能与状态持久化

```
防丢策略 (按优先级):
1. Store (Zustand/Pinia/Redux): 主内存状态 → 操作即时响应
2. sessionStorage: Store 的部分持久化 → 页面刷新可恢复
3. pendingOperations: 未同步操作的完整快照 → 断网可恢复
4. navigator.sendBeacon: beforeunload 时同步保存 → 页面关闭不丢数据
5. API save-draft: 定期后端持久化 → 跨设备恢复
```
