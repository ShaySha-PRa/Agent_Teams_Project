## 一、核心业务问题

### 1.1 问题陈述

> **来源**: `business_summary.md` §2.1 场景目标（双方共识）

**传统合同/法务文档审阅存在四个维度的结构化缺陷**：

| 问题维度 | 现象 | 根源 | 来源 |
|---------|------|------|------|
| **效率低下** | 一份 50 页商业合同需数小时至数天完成审阅；采购合同审批周期平均 5 天 | 高度依赖人工逐条阅读，无法并行处理 | `business_summary.md` §1.2 |
| **准确性不稳定** | 疲劳遗漏、知识盲区、标准不统一；主要法律 AI 平台幻觉率 17-33%，通用 LLM 仅识别 65-70% 交易要点 | 人工偏差 + LLM 概率式输出与法律确定性需求的根本性张力 | `business_summary.md` §1.2 + §2.1 |
| **一致性缺失** | 不同审阅者对同一风险条款判断标准不同；大型团队审阅标准难以统一 | 缺乏系统化的审阅规则引擎（Playbook）| `business_summary.md` §1.2 |
| **可追溯性不足** | 审计时难以回溯决策依据，缺少系统化的审阅过程记录 | 传统审阅过程缺乏结构化的决策日志 | `business_summary.md` §1.2 |

### 1.2 问题本质

> **来源**: `business_summary.md` §2.3: Teammate 2 核心洞察

当前 AI 技术在合同审阅场景中存在**非对称风险**：
- **误报（False Positive）可通过 HITL 有效控制** — interrupt 机制拦截率接近 100%
- **漏报（False Negative）控制仍然困难** — AI 看不到的风险不会被中断，依赖 AI 基础能力提升

这决定了系统的核心架构约束：**AI 作为"初筛加速器"，人类作为"最终决策者"**，两者之间的交互流程设计直接决定系统的可用性上限。

### 1.3 系统要解决的核心业务问题（收口定义）

> **来源**: 综合 `business_summary.md` §三 + `analysis_summary.md` §四

**本系统（Agent 智能文档审核系统）要解决的核心业务问题是**：

**在法律文档审阅场景中，构建一个以多 Agent 协作 AI 为驱动、以分级人机交互（HITL）为控制核心、以解释性数据透明展示为差异化优势的审阅加速系统，使得法务人员可以在 AI 完成初筛和风险预标记后，聚焦于高风险条款的精准判断，从而在确保法律合规的前提下实现 65-73% 的审阅时间节省。**

## 二、目标用户

> **来源**: `business_summary.md` §1.3 目标用户画像 + `analysis_summary.md` §三 竞品覆盖范围

### 2.1 用户分层

| 优先级 | 用户角色 | 典型场景 | 核心需求 | MVP 是否覆盖 |
|:------:|---------|---------|---------|:----------:|
| **P0** | 企业法务团队 | 日常合同审阅（采购、销售、服务协议等批量合同） | 提升效率，减少重复劳动，统一审阅标准 | ✅ |
| **P1** | 律师事务所律师 | 单次交易的合同审查、初稿质量把关 | 快速定位关键条款和风险点，辅助出具法律意见 | ✅ |
| **P1** | 企业合规部门 | 隐私政策、DPA 等合规文档的法规符合性检查 | 确保符合 GDPR/CCPA/PIPL 等法规要求 | ⚠️ 部分（MVP 阶段仅 NDA 合规检查） |
| **P2** | 知识产权管理人员 | 专利文件、许可协议的 IP 条款审阅 | 权利范围确认、侵权风险评估 | ❌ (MVP 后) |
| **P2** | HR 法务人员 | 劳动合同、竞业限制协议批量审阅 | 劳动法合规、模板偏离检测 | ❌ (MVP 后) |

### 2.2 MVP 阶段聚焦用户

> **来源**: `business_summary.md` §4.3 MVP 建议：双方报告一致认为 NDA 协议是 MVP 最佳切入点

**MVP 核心用户**: 企业法务团队（P0）+ 律师事务所律师（P1）
**MVP 场景边界**: NDA 协议（保密协议）审阅 — 标准化程度高、条款结构简单、法律风险可控

## 三、核心业务场景定义

### 3.1 场景分层总览

> **来源**: `business_summary.md` §3.1 可行性矩阵

───────────────────    ───────────────────    ───────────────────
NDA 协议审阅            采购/销售合同           软件许可协议
                       HR 文档                 M&A 尽职调查

### 3.2 MVP 核心业务场景（v1 必须覆盖）

> **来源**: `business_summary.md` §4.3 + §3.1 可行性矩阵 + `analysis_summary.md` §4.1 行业基线

#### 场景 1：NDA 协议 AI 辅助审阅

| 维度 | 定义 | 来源 |
|------|------|------|
| **场景目标** | 法务人员上传 NDA 协议，AI 自动完成条款提取、风险识别、合规检查，人工仅最终确认 | `business_summary.md` §1.1 业务目标 |
| **输入** | PDF / DOCX 格式的 NDA 协议文件 | `analysis_summary.md` §4.1: 行业标配 |
| **输出** | 包含风险分级标记、修改建议、解释性数据的审阅报告 | `analysis_summary.md` §3.3 市场空白 #1 #3 |
| **AI 自动化环节** | 条款结构化提取、标准化条款对比 Playbook、合规检查、关键日期/金额提取、条款缺失检测、初步风险分级 | `business_summary.md` §2.6: 适合 AI 自动化的环节 |
| **人工确认环节** | 高风险条款最终判定、模糊条款解释、最终审阅意见签署 | `business_summary.md` §2.6: 需要人工介入的环节 |
| **HITL 模式** | 分级告警：高风险（红色 100% 强制审核）→ 中风险（黄色批量选择性审核）→ 低风险（绿色自动通过+抽样） | `business_summary.md` §4.1 |
| **成功指标** | 审阅时间从 ~56 分钟缩减至 ~15-20 分钟（65-73% 节省） | `business_summary.md` §1.2: 行业效率数据 |

#### 场景 2：审阅结果解释与决策追溯

| 维度 | 定义 | 来源 |
|------|------|------|
| **场景目标** | 审核员查看 AI 风险标记时，系统提供完整的解释链：判定依据 → 相关条款原文 → Playbook 标准条款对比 → 置信度评分 | `analysis_summary.md` §3.3: 解释性数据透明展示（最大差异化机会） |
| **输入** | AI 生成的风险标记列表（含风险等级、类别、判定理由） | `analysis_summary.md` §4.1: 行业基线 - 风险分级标记 |
| **输出** | 并排视图（左：合同原文 + 高亮定位，右：风险分析 + 解释链 + 操作区） | `analysis_summary.md` §4.1: 行业基线 - 并排视图 |
| **解释链数据** | AI 置信度、Playbook 规则引用、相关法规原文引用、历史相似条款审阅决策 | `analysis_summary.md` §3.3: 解释性数据维度分解 |
| **决策操作** | 确认（approve）、否决并修正（edit/reject）、手动补充风险标记 | `business_summary.md` §3.2: Command(resume=...) 四种决策类型 |

#### 场景 3：审阅审计追踪与报告生成

| 维度 | 定义 | 来源 |
|------|------|------|
| **场景目标** | 完整记录 AI 标记 → 人工裁定 → 最终输出的决策链路，生成可签署的审阅报告 | `analysis_summary.md` §4.2: 审计追踪可视化（P1 差异化） |
| **输入** | 审阅过程中所有 AI 标记和人工裁定记录 | `business_summary.md` §1.2: 可追溯性需求 |
| **输出** | 审阅报告（含风险摘要、高风险条款清单、中风险条款清单、审计追踪日志） | `analysis_summary.md` §3.2 呈现维度 - 报告与导出 |
| **审计记录粒度** | 每个风险标记的：timestamp + AI 置信度 + 人工裁定类型 + 最终输出状态 | `business_summary.md` §4.1: 三层反馈闭环 |

### 3.3 场景间的数据关系

```
场景 1（AI 辅助审阅）         场景 2（结果解释与决策）       场景 3（审计追踪与报告）
       │                            │                          │
       │ 生成 AI 标记                │ 消费 AI 标记              │ 消费 AI 标记 + 人工裁定
       │                            │                          │
       ├─ 条款提取结果 ──────────────▶│ 原文定位 + 高亮           │
       ├─ 风险分级标记 ──────────────▶│ 风险卡片展示             ├─ 审计日志条目
       ├─ AI 判定依据 ───────────────▶│ 解释链数据               ├─ 风险摘要
       └─ Playbook 对比 ─────────────▶│ 标准条款 diff            ├─ 最终报告
                                     │                          │
                                     │ 产出人工裁定              │
                                     ├─ confirm/edit/reject ───▶│ 决策记录
                                     └─ 手动补充标记 ───────────▶│ 补充标记记录
```

## 四、从功能清单到业务建模的数据升级

### 4.1 功能清单（What）→ 业务实体（What Data）

> **来源**: 综合 `business_summary.md` 流程描述 + `analysis_summary.md` 呈现维度

| 功能 | 输入数据 | 处理 | 输出数据 | 涉及的业务实体 |
|------|---------|------|---------|-------------|
| 文档上传 | 文件二进制流 + 格式类型 + 上传元数据 | 格式识别 → 预处理 → 存储 | 文档 ID + 文档状态 | **Document** |
| 条款提取 | Document.raw_text | 分段 → NER → 结构化 | 条款 ID + 条款类型 + 条款文本 + 位置区间 | **Clause** |
| 风险识别 | Clause 列表 + Playbook 规则 | AI/规则引擎 分析 | 风险标记 ID + 风险等级 + 风险类别 + 判定依据 | **RiskFlag** |
| 人工审核 | RiskFlag 列表 + 合同原文 | 人工判定 | 裁定类型 + 裁定备注 + 裁定时间 | **ReviewDecision** |
| Playbook 对比 | Clause + Playbook.standard_clause | diff | 差异项 + 偏离程度 | **PlaybookRule** |
| 报告生成 | Document + Clause + RiskFlag + ReviewDecision | 汇总 → 格式化 | 审阅报告 ID + 报告内容 | **ReviewReport** |
| 审计追踪 | ReviewDecision 时间序列 | 日志聚合 | 审计条目 ID + 操作时间线 | **AuditLog** |

### 4.3 实体定义（业务建模级，非数据库 Schema）

> **注**: 以下为业务建模定义，用于后续数据模型设计（`docs/07_data_model/`）的输入。字段列表为业务属性，非最终数据库列。

#### Document（文档）
- 业务含义：一份待审阅的合同/法务文档
- 关键业务属性：文件标识、格式类型、上传时间、文档状态、页数/大小、所属项目

#### Clause（条款）
- 业务含义：从文档中提取的结构化条款单元
- 关键业务属性：条款类型、原文文本、在文档中的位置区间、所属文档引用

#### RiskFlag（风险标记）
- 业务含义：AI 对某个条款生成的风险判定
- 关键业务属性：风险等级（高/中/低）、风险类别、AI 置信度、判定依据文本、关联条款引用、关联 Playbook 规则引用、标记状态（待审核/已确认/已否决/已修正）

#### ReviewDecision（审阅决策）
- 业务含义：人类审核员对 AI 风险标记的裁定
- 关键业务属性：裁定类型（approve/edit/reject）、裁定备注、裁定时间戳、裁定人标识、关联风险标记引用

#### PlaybookRule（审阅规则）
- 业务含义：企业自定义的合同审阅标准
- 关键业务属性：规则名称、适用文档类型、标准条款文本、风险判定逻辑、风险等级

#### AuditLog（审计日志）
- 业务含义：不可篡改的操作记录
- 关键业务属性：操作时间戳、操作类型、操作人/Agent 标识、关联实体引用、操作前后状态快照

#### ReviewReport（审阅报告）
- 业务含义：一次完整审阅的汇总输出
- 关键业务属性：报告生成时间、风险摘要统计、高风险条款清单、修改建议清单、审计追踪摘要、签署状态

## 五、MVP 范围边界

### 5.1 MVP 包含（v1）

| 维度 | 范围 | 来源 |
|------|------|------|
| **文档类型** | **仅 NDA 协议**（保密协议） | `business_summary.md` §4.3 |
| **文档格式** | PDF + DOCX | `analysis_summary.md` §4.1 行业基线 |
| **AI 能力** | 条款提取 + 风险分级标记（高/中/低） + Playbook 对比 + 合规检查（仅 NDA 相关法规） | `business_summary.md` §2.6 适合 AI 自动化 |
| **HITL 能力** | 分级告警：高（强制人工）→ 中（批量可选）→ 低（自动通过） | `business_summary.md` §4.1 |
| **呈现方式** | Web 平台：并排视图（左文档右分析）+ 风险仪表盘 | `analysis_summary.md` §4.3: Web 优先 |
| **解释性数据** | AI 置信度 + Playbook 规则引用 + 合同原文定位 | `analysis_summary.md` §4.2: P0 差异化 |
| **审计追踪** | 基础审计日志（AI 标记 + 人工裁定时间线） | `analysis_summary.md` §4.1 行业基线 |
| **报告导出** | PDF 审阅报告 | `analysis_summary.md` §3.2 |
| **用户角色** | 企业法务（P0）+ 律师（P1） | 本文 §2.1 |

### 5.2 MVP 明确不包含

| 维度 | 排除原因 | 计划阶段 |
|------|---------|---------|
| 采购/销售/HR/IP 等其他合同类型 | 复杂度和风险梯度超出 MVP 范围 | v2 |
| 多文档关联导航（合同家族图谱） | 单文档 NDA 场景不涉及跨文档引用 | v2 |
| MS Word 插件 | MVP 聚焦 Web 平台验证核心价值 | v2 |
| 移动端 | 全面的市场空白，但 MVP 优先桌面端 | v2+ |
| 跨法域合同审阅 | 当前 AI 能力不可行（`business_summary.md` §3.1 可行性矩阵） | v3 |
| AI 误判修正闭环（反馈学习） | 需要足够的审核数据累积 | v3 |
| Playbook 协作编辑 | 单人使用场景 MVP 阶段不涉及 | v3 |

## 六、对下游设计的衔接指引

### 6.1 对系统架构设计的输入

- 多 Agent 架构模式：Supervisor + 条款提取 Agent + 风控 Agent + 合规 Agent + 报告 Agent（`business_summary.md` §3.4）
- HITL 中断机制：LangGraph `interrupt()` + `Command(resume=...)` + Checkpointer（`business_summary.md` §3.2）
- 分级告警的架构约束：高风险条款的 interrupt 不可跳过（`business_summary.md` §4.1）

### 6.2 对前端原型的输入

- 核心页面：文档上传页 → 审阅工作台（并排视图）→ 风险审核面板 → 报告预览页

- 差异化 UI：AI 判定依据的解释链展示（竞品普遍缺失的能力）

### 6.3 对数据模型设计的输入

- 7 个核心业务实体（本文 §4.3）
